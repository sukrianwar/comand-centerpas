Daftar Isi

1. Latar Belakang
Perusahaan yang memiliki petugas keamanan (security) membutuhkan sistem untuk memastikan setiap patroli dilakukan sesuai jadwal dan rute yang telah ditentukan. Saat ini proses patroli masih dilakukan secara manual menggunakan buku patroli sehingga memiliki beberapa kendala, seperti:
Sulit mengetahui apakah petugas benar-benar melakukan patroli.
Tidak ada bukti waktu patroli secara real-time.
Sulit membuat laporan patroli.
Sulit mengetahui apabila terdapat titik patroli yang terlewat.
Pelaporan temuan masih menggunakan WhatsApp sehingga data tidak terpusat.
Aplikasi Guard Tour dibuat untuk mendigitalisasi proses patroli sehingga seluruh aktivitas security dapat dipantau secara real-time.
2. Tujuan Produk
Membangun sistem Guard Tour yang mampu:
Memastikan seluruh checkpoint dikunjungi sesuai jadwal.
Mencatat waktu patroli secara otomatis dan tidak dapat dimanipulasi (server-time based).
Menyediakan bukti patroli menggunakan QR Code statis dengan validasi lokasi wajib.
Melaporkan temuan secara langsung dengan alur approval yang jelas.
Menampilkan monitoring patroli secara real-time beserta notifikasi eskalasi.
Menghasilkan laporan patroli secara otomatis.
Berjalan mandiri di infrastruktur internal perusahaan (on-premise) tanpa bergantung pada koneksi internet publik.

Ketentuan Anti-Fraud
Validasi lokasi (GPS + radius) bersifat wajib, bukan opsional.
Saat online, timestamp scan diambil dari server time pada saat data diterima server, bukan jam perangkat, untuk mencegah manipulasi waktu.
Saat offline, aplikasi menghitung selisih waktu (offset) antara jam perangkat dan jam server terakhir kali perangkat online, lalu menerapkan offset tersebut ke timestamp data yang direkam offline — sehingga waktu tetap akurat meski jam perangkat sedikit berbeda dengan jam server.  [v1.4]
Data hasil scan offline yang selisih waktunya dengan server dianggap tidak wajar (mis. jam perangkat sengaja diubah jauh) akan ditandai sebagai "Perlu Verifikasi" pada dashboard Supervisor untuk ditinjau manual.  [v1.4]

Data foto bukti (jika diaktifkan) divalidasi metadata waktu & lokasinya.
14. Modul Offline Mode & Antrian Sinkronisasi
Beberapa titik checkpoint (basement, ruang panel, parkiran bawah tanah) berpotensi berada di luar jangkauan WiFi kantor. Modul ini memastikan aktivitas patroli tetap tercatat secara akurat meski perangkat security terputus sementara dari jaringan WiFi kantor, dengan data dikirim otomatis begitu koneksi kembali tersedia.
Cara Kerja
Aplikasi Web (PWA — Progressive Web App) secara berkala memeriksa status koneksi ke jaringan WiFi kantor.
Selama terhubung, setiap hasil scan checkpoint langsung dikirim dan disimpan ke server (Mysql).
Saat koneksi terputus, aplikasi otomatis beralih ke Mode Offline: hasil scan (checkpoint, waktu, lokasi, foto) disimpan sementara di penyimpanan lokal perangkat (IndexedDB pada browser), bukan dikirim ke server.
Setiap data offline dicatat ke dalam antrian (queue) lokal dengan status "Menunggu Sinkronisasi", lengkap dengan timestamp saat data direkam di perangkat.
Guard tetap dapat melanjutkan patroli checkpoint berikutnya tanpa hambatan; setiap hasil scan baru otomatis masuk ke antrian yang sama.
Begitu perangkat kembali terhubung ke WiFi kantor, aplikasi otomatis mengirim seluruh data dalam antrian ke server secara berurutan (FIFO — First In, First Out) tanpa perlu aksi manual dari guard.
Setelah suatu data berhasil dikirim dan dikonfirmasi tersimpan server, data tersebut dihapus dari antrian lokal dan statusnya berubah menjadi "Tersinkron".
Timestamp resmi yang tercatat di server tetap mengacu pada waktu saat data direkam di perangkat (offline), bukan waktu saat data terkirim, sehingga akurasi waktu kunjungan checkpoint tetap terjaga.
Fitur Pendukung
Indikator status koneksi (Online/Offline) ditampilkan jelas di halaman utama Web App Patrol.
Badge jumlah data yang masih dalam antrian ("3 data menunggu sinkronisasi") agar guard mengetahui progres pengiriman.
Retry otomatis dengan jeda bertahap (exponential backoff) apabila percobaan kirim gagal, agar tidak membebani jaringan saat baru tersambung kembali.
Data di penyimpanan lokal tetap aman tersimpan meskipun browser/tab ditutup atau perangkat dimatikan, dan akan otomatis dilanjutkan pengirimannya saat aplikasi dibuka kembali.
Notifikasi ke Admin apabila terdapat data yang gagal sinkron dalam waktu lama (lihat tabel eskalasi bab 15).
Ketentuan & Batasan
Foto bukti temuan/incident yang diambil saat offline turut disimpan sementara di perangkat dan ikut dikirim saat sinkronisasi; ukuran file dikompresi otomatis agar tidak memenuhi kapasitas penyimpanan lokal.
Resolusi konflik data (mis. jika ada perubahan jadwal saat guard offline) ditangani di sisi server berdasarkan timestamp asli data direkam.
Panic Button tetap memerlukan koneksi aktif karena sifatnya darurat/real-time (lihat bab 16) — tidak dimasukkan ke dalam antrian offline.

20. Non-Functional Requirement
20.1 Performance
Response < 3 detik pada jaringan lokal
Support 500 user aktif
20.2 Security
JWT Authentication dengan refresh token
HTTPS internal (self-signed/internal CA) untuk trafik dalam jaringan lokal
Password Hashing
Role Based Access Control (RBAC)
Server-time based timestamp untuk seluruh pencatatan aktivitas
Akses sistem dibatasi hanya dari dalam jaringan internal perusahaan
20.3 Availability
Uptime 99% pada jam operasional
Karena single server on-premise, perlu prosedur monitoring kesehatan server (health check) oleh Admin/IT internal.
20.4 Compatibility
Browser: Chrome, Edge, Firefox (desktop untuk Dashboard)
Browser mobile: Chrome/Safari Android & iOS (untuk Web App Patrol, dengan dukungan akses kamera & GPS)
20.5 Data Privacy & Kepatuhan
Kepatuhan terhadap UU Perlindungan Data Pribadi (UU PDP) terkait data lokasi (GPS) karyawan, meski data tidak keluar dari jaringan internal perusahaan.
Persetujuan (consent) karyawan atas pelacakan lokasi selama jam kerja/shift.
Kebijakan retensi data lokasi & foto (mis. disimpan maksimal 90 hari, dapat dikonfigurasi).
Data pribadi hanya dapat diakses oleh role yang berwenang dan dari dalam jaringan internal.
20.6 Audit Trail
Mencatat setiap perubahan pada data master (User, Area, Checkpoint, Jadwal): siapa, kapan, perubahan apa.
Log audit tidak dapat dihapus atau diubah oleh user biasa (append-only).
Tersedia fitur pencarian & filter log audit untuk keperluan investigasi/audit internal.
20.7 File Storage
Foto & video incident disimpan pada storage lokal server / NAS internal perusahaan (bukan cloud storage).
Kompresi otomatis untuk foto/video sebelum disimpan guna menghemat kapasitas disk server.
Kebijakan retensi media & kapasitas disk perlu direncanakan sejak awal (estimasi pertumbuhan data per bulan).
Direkomendasikan backup storage terpisah dari server utama (mis. NAS kedua) untuk redundansi.
20.8 API Design
API menggunakan versioning (mis. /api/v1/...) untuk mendukung perubahan ke depan tanpa breaking existing client, termasuk saat Mobile App Fase 2 dikembangkan.
Rate limiting untuk mencegah penyalahgunaan meski dalam jaringan internal.
Dokumentasi API (mis. OpenAPI/Swagger) disiapkan agar Mobile App Fase 2 dapat mengonsumsi API yang sama tanpa perubahan besar.
20.9 Backup & Disaster Recovery
Backup database Mysql terjadwal (harian) dengan retensi minimal 30 hari, disimpan di media terpisah dari server utama.
Prosedur restore teruji secara berkala — penting karena tidak ada redundansi otomatis seperti pada layanan cloud.
Recovery Time Objective (RTO) dan Recovery Point Objective (RPO) didefinisikan sesuai kebutuhan operasional perusahaan.
Dipertimbangkan penyediaan server cadangan (standby) untuk meminimalkan downtime jika server utama bermasalah.
20.10 Infrastruktur Jaringan Lokal
Diperlukan survei & pemetaan cakupan WiFi di seluruh titik checkpoint sebelum go-live, khususnya area basement/ruang panel/parkiran.
Direkomendasikan segmentasi jaringan (VLAN) khusus untuk perangkat Guard Tour demi keamanan & stabilitas.
Server memerlukan IP/hostname internal tetap agar mudah diakses seluruh perangkat di jaringan kantor.
Akses remote (dari luar kantor) tidak didukung di Fase 1; jika dibutuhkan, direkomendasikan menggunakan VPN internal sebagai pengembangan lanjutan.
21. Database
21.1 Teknologi Database
DBMS: MySQL. 
Dipilih karena: bersifat open-source (tanpa biaya lisensi, sesuai model deployment on-premise), mendukung relasi data yang kompleks (user, jadwal, patrol log, incident), serta memiliki performa yang stabil untuk menangani beban transaksi menengah (±500 pengguna aktif). 
Koneksi API Backend menggunakan driver MySQL yang terintegrasi dengan framework Laravel untuk mengelola koneksi database secara efisien. 
Backup dilakukan menggunakan utilitas bawaan MySQL (mysqldump) untuk pencadangan data secara berkala sehingga mendukung proses pemulihan data apabila terjadi kegagalan sistem.
